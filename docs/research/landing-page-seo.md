# SEO for nibble's landing page

Research only: nothing under `site/` was changed. Every source was read on 2026-11-11, and the live site (`https://nibble.tonytang.dev`) was fetched the same day. Sources are the search engines' and vendors' own documentation; where I could not confirm something against one, the text says so.

Two things frame everything below:

- **The site is hours old.** The GitHub repository was created on 2026-11-11 and has 0 stars, no topics and no custom social image (`gh repo view tonytangdev/nibble`). The only inbound links I found are from `tonytang.dev/apps/` and the repository's homepage field. Getting discovered and indexed matters more right now than fine-tuning.
- **Google and Bing both say there is no separate "AI SEO".** The same crawlable, clearly worded page serves classic search and AI answers ([Google](https://developers.google.com/search/docs/fundamentals/ai-optimization-guide), [Bing](https://www.bing.com/webmasters/help/webmaster-guidelines-30fba23a)).

## Summary: what matters most, in order

1. **Add a social preview image and the missing Open Graph and X card tags.** The page has no `og:image` and no `og:url`, two of the four properties the Open Graph protocol requires, and no `twitter:card`. Links shared on X, Slack, Discord and the like show no image today. For a developer tool that spreads by people pasting the link, this is the biggest visible gap.
2. **Put the words people search for in the title and the main heading.** Today neither says "Claude Code", "menu bar", "macOS" or "usage". Google's Search Essentials name this as a key practice. The wording is the owner's call (see Open questions).
3. **Register the site with Google Search Console and Bing Webmaster Tools, and ask for indexing.** A new site with few links is exactly the case where Google says it might not find the page on its own.
4. **Add `rel="canonical"`, a `robots.txt`, a one-URL sitemap, and redirect HTTP to HTTPS.** `http://nibble.tonytang.dev/` answers `200` with the full page instead of redirecting. Each fix is minutes of work.
5. **Add JSON-LD: `WebSite` (for the site name in results) and `SoftwareApplication` (to describe the app).** Without `WebSite` data on the subdomain, Google may show the parent domain's site name. Be clear about the limit: nibble cannot get the software-app rich result, because Google requires a rating or review for it and nibble has none.

Not worth doing for search: an FAQ block for rich results (Google removed the feature in 2026), an `llms.txt` (Google says it ignores it; no AI vendor's crawler documentation mentions reading one), a `keywords` meta tag (Google does not use it).

## Findings by topic

### 1. Title links and snippets

- Google builds the title link from several sources: the `<title>` element, the main visual title, heading elements, `og:title`, other prominent text, anchor text of links to the page, and `WebSite` structured data. It asks for "descriptive and concise" titles, warns against keyword stuffing, and says the home page title is "a reasonable place to include some additional information about your site", giving the form `ExampleSocialSite, a place for people to meet and mingle`. There is no length limit; the link is cut to fit the device. ([Title links](https://developers.google.com/search/docs/appearance/title-link))
- Google's Search Essentials list as a key practice: "Use words that people would use to look for your content, and place those words in prominent locations on the page, such as the title and main heading of a page, and other descriptive locations such as alt text and link text." ([Search Essentials](https://developers.google.com/search/docs/essentials))
- Snippets come mainly from the page's own text. Google "sometimes" uses the meta description when it describes the page better. There is no length limit, and a description made of keywords is less likely to be shown. ([Snippets](https://developers.google.com/search/docs/appearance/snippet))
- Bing: "Missing, duplicate, or overly short title tags and meta descriptions may reduce indexing reliability, ranking, and eligibility for grounding results and citations." It also asks to "align titles, heading, and content intent", to "surface key information early", and to name products clearly and consistently. ([Bing Webmaster Guidelines](https://www.bing.com/webmasters/help/webmaster-guidelines-30fba23a), sections 13 and 16 to 18)
- Google does not use the `keywords` meta tag. ([SEO Starter Guide](https://developers.google.com/search/docs/fundamentals/seo-starter-guide))

What this means for nibble: the title and `h1` ask a good question but contain none of the words a developer would type ("Claude Code", "usage", "cost", "menu bar", "macOS", "subscription vs API"). The meta description is already good. The body text does contain those words, so the page is not invisible for them; they are simply not in the two places both engines weigh most.

### 2. Crawling, indexing and canonical URLs

**2.1 Canonical.** Google picks a canonical URL from a cluster of duplicates using, in order of strength: redirects (strong), `rel="canonical"` (strong), sitemap inclusion (weak). It recommends a self-referencing canonical on the canonical page itself, written as an absolute URL. It prefers HTTPS over HTTP by default and says you can make sure of it by redirecting HTTP to HTTPS. ([Canonicalization](https://developers.google.com/search/docs/crawling-indexing/canonicalization), [How to specify a canonical](https://developers.google.com/search/docs/crawling-indexing/consolidate-duplicate-urls)) Bing: duplicate URLs "reduce Bing's confidence in selecting a URL for grounding results or citations". ([Bing Webmaster Guidelines](https://www.bing.com/webmasters/help/webmaster-guidelines-30fba23a))

The page currently has two live duplicates of the home URL: the HTTP version and any URL with a query string.

**2.2 HTTP to HTTPS.** Every `.dev` domain is on browsers' HSTS preload list, so a browser never loads the HTTP version ([get.dev](https://get.dev/)). Crawlers and link-preview fetchers are not browsers, so the `200` on HTTP is still a duplicate for them. Cloudflare's "Always Use HTTPS" setting redirects all HTTP requests "for all subdomains and hosts" of the zone ([Cloudflare](https://developers.cloudflare.com/ssl/edge-certificates/additional-options/always-use-https/)). Cloudflare's own HSTS setting is zone-wide; for one subdomain it suggests a response header rule ([Cloudflare HSTS](https://developers.cloudflare.com/ssl/edge-certificates/additional-options/http-strict-transport-security/)). Given the preload list, an HSTS header adds little here.

**2.3 robots.txt.** A missing robots.txt is not an error: Google treats a `404` as "no crawl restrictions" ([Google's robots.txt rules](https://developers.google.com/search/docs/crawling-indexing/robots/robots_txt)), and RFC 9309 says the same for an "unavailable" file ([RFC 9309, section 2.3.1.3](https://www.rfc-editor.org/rfc/rfc9309.html)). The file must sit at `/robots.txt` on the host it governs, and "a robots.txt on a subdomain is only valid for that subdomain". Its `sitemap:` line must be an absolute URL and is read by Google, Bing and others. Robots.txt controls crawling, not indexing ([Bing](https://www.bing.com/webmasters/help/webmaster-guidelines-30fba23a), section 10). So a robots.txt is optional for Google; its value here is the sitemap line and a stated position on AI crawlers (section 5).

**2.4 Sitemap: does one page need one?** Google: "you might not need a sitemap" if the site is small (about 500 pages or fewer) and fully linked; "you might need" one if "your site is new and has few external links to it". ([Sitemaps overview](https://developers.google.com/search/docs/crawling-indexing/sitemaps/overview)) Bing is firmer: it lists XML sitemaps and IndexNow first among discovery signals and wants accurate `lastmod` values. ([Bing Webmaster Guidelines](https://www.bing.com/webmasters/help/webmaster-guidelines-30fba23a), sections 2 and 3) In the protocol, `lastmod`, `changefreq` and `priority` are optional, and `priority` "is not likely to influence the position of your URLs" ([sitemaps.org](https://www.sitemaps.org/protocol.html)). Conclusion: Google would cope without one, but nibble fits the "new, few links" case and Bing asks for one, so a one-URL sitemap with a true `lastmod` is worth its few lines.

**2.5 Getting indexed.**

- Google finds pages mainly through links from pages it already knows ([SEO Starter Guide](https://developers.google.com/search/docs/fundamentals/seo-starter-guide)). You can ask for a crawl with the URL Inspection tool in Search Console; crawling "can take anywhere from a few days to a few weeks" and is not guaranteed ([Ask Google to recrawl](https://developers.google.com/search/docs/crawling-indexing/ask-google-to-recrawl)).
- A Search Console Domain property for `tonytang.dev` covers every subdomain and protocol, `nibble.tonytang.dev` included; it is verified by a DNS record ([Search Console Help](https://support.google.com/webmasters/answer/34592)). If the owner already has one, nibble is already inside it.
- IndexNow is a single HTTP request that tells participating engines a URL changed. It needs a key file hosted on the site. The engines listed today are Bing, Yandex, Seznam, Naver, Yep, the Internet Archive and Amazonbot; **Google is not among them**. Its FAQ says it is useful "even for small websites". ([IndexNow documentation](https://www.indexnow.org/documentation), [FAQ](https://www.indexnow.org/faq), [list of engines](https://www.indexnow.org/searchengines.json))
- OpenAI's ChatGPT search, and Microsoft's Copilot, are separate consumers: Bing says its guidelines govern Copilot and its grounding API too ([Bing Webmaster Guidelines](https://www.bing.com/webmasters/help/webmaster-guidelines-30fba23a)). I did not find a primary source stating which index ChatGPT search draws on, so I make no claim about it.

**2.6 Status codes.** Google does not index URLs that return `4xx`, and treats `307` like `302` ([HTTP status codes](https://developers.google.com/search/docs/crawling-indexing/http-network-errors)). The site's real `404` for unknown paths is correct. Cloudflare's default HTML handling produces the `307` from `/index.html` to `/` ([Cloudflare HTML handling](https://developers.cloudflare.com/workers/static-assets/routing/advanced/html-handling/)); nothing links to `/index.html`, so this needs no change.

**2.7 Mobile-first indexing.** Google indexes the page as its smartphone crawler sees it, and recommends responsive design, where the same HTML is served to every device ([Mobile-first indexing](https://developers.google.com/search/docs/crawling-indexing/mobile/mobile-sites-mobile-first-indexing)). The page is responsive and serves one HTML, so it already complies. The download script only changes a link and a label in the browser.

**2.8 Images.** Google indexes images referenced by `<img src>` and "doesn't index CSS images"; alt text is "the most important attribute" for understanding an image ([Google Images best practices](https://developers.google.com/search/docs/appearance/google-images)). The hero is drawn in HTML and CSS, so the page offers image search nothing but the app icon. Real screenshots exist in `docs/screenshots/` (680×960). Google's AI guide also says to support text with "high-quality images" ([AI optimization guide](https://developers.google.com/search/docs/fundamentals/ai-optimization-guide)).

### 3. Structured data

- Google recommends JSON-LD, says markup must describe content that is visible on the page, and does not guarantee that any feature appears. Fake reviews are named as a violation. ([General guidelines](https://developers.google.com/search/docs/appearance/structured-data/sd-policies), [Introduction](https://developers.google.com/search/docs/appearance/structured-data/intro-structured-data)) Bing: structured data "must accurately reflect visible content" and "does not guarantee visibility" ([Bing Webmaster Guidelines](https://www.bing.com/webmasters/help/webmaster-guidelines-30fba23a), section 14).
- **`SoftwareApplication`.** Still a supported rich result. Required: `name`, `offers.price` (set to `0` for a free app), and **a rating or a review** (`aggregateRating` or `review`). Recommended: `applicationCategory` from a fixed list (it includes `DeveloperApplication` and `UtilitiesApplication`) and `operatingSystem`. ([Software app](https://developers.google.com/search/docs/appearance/structured-data/software-app)) nibble has no ratings, so it **cannot qualify for the rich result today**, and inventing a rating would break the guidelines. The markup is still valid schema.org ([schema.org/SoftwareApplication](https://schema.org/SoftwareApplication) defines `downloadUrl`, `softwareVersion`, `operatingSystem`, `applicationCategory`) and Bing says such data "may support clearer grounding". The Rich Results Test will report the missing rating; that is expected.
- **`WebSite` and the site name.** Google's site name is per domain or subdomain. "To indicate your site name preference, add `WebSite` structured data to your home page"; it also reads `og:site_name`, the `<title>` and headings. Required properties: `name` and `url`. And the line that matters for a subdomain: "If there's no structured data on the subdomain's home page, then the domain-level site name may be used for the subdomain as a fallback." Without it, results for nibble may be labelled with whatever name Google holds for `tonytang.dev`. Google also notes it generally will not give the same site name to two sites, so a short common word like "nibble" may not be granted; `alternateName` lets you offer fallbacks, including the lowercase host name. The data should be the same on HTTP and HTTPS duplicates. ([Site names](https://developers.google.com/search/docs/appearance/site-names))
- **`Organization`.** Meant for an organization's own home page (logo, legal details, knowledge panel); it has no required properties ([Organization](https://developers.google.com/search/docs/appearance/structured-data/organization)). nibble's page is about a product by one person, so this type fits poorly. An `author` of type `Person` inside the `SoftwareApplication` is the honest equivalent; that is my judgement, not a Google recommendation.
- **FAQ.** Google's FAQ rich result is gone. The changelog entry of 2026-05-08 says "This feature will no longer appear in Google Search starting May 7, 2026", and on 2026-06-15 Google removed its documentation; the old URL now redirects to the changelog. ([Search documentation updates](https://developers.google.com/search/updates)) An FAQ section may still be useful to readers, but there is no rich result to earn with `FAQPage` markup.
- In June 2025 Google also retired seven lesser-used types (Book Actions, Course Info, Claim Review, Estimated Salary, Learning Video, Special Announcement, Vehicle Listing); none concerns nibble ([Search Central blog](https://developers.google.com/search/blog/2025/06/simplifying-search-results)).

### 4. Page experience and Core Web Vitals

- "Core Web Vitals are used by our ranking systems." Beyond them, "other page experience aspects don't directly help your website rank higher". Google also warns that chasing a perfect score for SEO "may not be the best use of your time". The self-check list includes HTTPS, mobile display, and no intrusive interstitials. ([Page experience](https://developers.google.com/search/docs/appearance/page-experience))
- Targets: LCP within 2.5 s, INP under 200 ms, CLS under 0.1 ([Core Web Vitals](https://developers.google.com/search/docs/appearance/core-web-vitals)), judged at the 75th percentile of real page loads ([web.dev](https://web.dev/articles/vitals)).
- CSS is render-blocking by default ([web.dev](https://web.dev/articles/critical-rendering-path/render-blocking-css)). web.dev advises care with font preloading, since preload ignores `unicode-range` ([web.dev font best practices](https://web.dev/articles/font-best-practices)).
- Cloudflare serves static assets with `Cache-Control: public, max-age=0, must-revalidate` by default; a `_headers` file in the asset directory can override it, and Cloudflare's own example sets a year-long `immutable` policy on hashed files ([Cloudflare headers](https://developers.cloudflare.com/workers/static-assets/headers/)).

What this means for nibble: nothing here looks at risk. The page is small, static, compressed, has no third-party script and declares image dimensions. The only cheap gain is long caching for the hashed files under `/assets/`, which helps repeat visits, not rankings. I have not measured the vitals.

### 5. The site name and favicon in results

- Site name: see section 3.
- Favicon: Google reads `<link rel="icon">` (also `apple-touch-icon`) from the home page, one favicon per host name, and a subdomain can have its own. The file must be square, at least 8×8 px, "we recommend using a favicon that's larger than 48x48px". Supported formats: BMP, GIF, ICO, PNG, JPEG, PPM, TIFF. **SVG is not on the list.** "The favicon URL must be stable (don't change the URL frequently)." Googlebot-Image must be allowed to fetch it. ([Favicon in Search](https://developers.google.com/search/docs/appearance/favicon-in-search))

nibble's 64×64 PNG qualifies. Its URL carries a content hash, so it changes only when the icon changes; a fixed `/favicon.png` would remove even that, at no cost.

### 6. A subdomain of a personal domain

- Google gives no ranking preference between subdomains and subdirectories: "do whatever makes sense for your business". The TLD does not matter either, apart from country targeting. ([SEO Starter Guide](https://developers.google.com/search/docs/fundamentals/seo-starter-guide))
- A subdomain is treated as its own site for the site name, the favicon and robots.txt (sections 2.3, 3 and 5).
- In Search Console, the subdomain inherits the parent Domain property's data and settings, including the "Search generative AI control" (section 7).
- I found no primary source saying a subdomain does or does not inherit ranking strength from its parent domain. Treat any such claim as unverified.

### 7. Social and link previews

**Open Graph.** "The four required properties for every page are" `og:title`, `og:type`, `og:image` and `og:url`. `og:url` is "the canonical URL of your object". Recommended extras include `og:description`, `og:site_name` and `og:locale`. For the image: `og:image:width`, `og:image:height`, `og:image:type`, and "if the page specifies an og:image it should specify `og:image:alt`". ([ogp.me](https://ogp.me/)) The protocol sets no image size. Every example there uses an absolute URL; it does not say whether a relative one is allowed, so use an absolute one.

**X cards.** The current X developer site no longer serves its Cards pages: the old URLs redirect to `docs.x.com/overview`. I read them from the Wayback Machine's copies of February 2026 ([summary card with large image](https://web.archive.org/web/20260204074639/https://developer.x.com/en/docs/x-for-websites/cards/overview/summary-card-with-large-image), [Cards markup](https://web.archive.org/web/20260201012312/https://developer.x.com/en/docs/x-for-websites/cards/overview/markup)). They may no longer describe what X does. They say:

- `twitter:card` is required and must be `summary_large_image` for the large image card. `twitter:title` is required; `twitter:site`, `twitter:description`, `twitter:image` and `twitter:image:alt` (420 characters at most) are optional.
- X falls back to Open Graph: `og:title`, `og:description`, `og:image` and `og:image:alt` are used when the `twitter:` versions are absent. So one extra tag, `twitter:card`, is enough once the Open Graph set is complete.
- Image: "aspect ratio of 2:1 with minimum dimensions of 300x157 or maximum of 4096x4096 pixels", under 5 MB, JPG, PNG, WEBP or GIF. "SVG is not supported."
- The image should be "unique" to the page, not "a generic image such as your website logo".

I did not check other platforms' image rules (Facebook, LinkedIn, Slack, Discord) against their own documentation, so the often-quoted 1200×630 size is not confirmed here. A 2:1 PNG satisfies X's stated rule, and GitHub recommends the same shape for a repository's social preview: 1280×640, under 1 MB ([GitHub Docs](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/customizing-your-repositorys-social-media-preview)). One 1280×640 image can serve both.

### 8. AI search and crawlers

**Google.** "There are no additional requirements to appear in AI Overviews or AI Mode, nor other special optimizations necessary." A page must be indexed and eligible for a snippet. Googlebot's robots.txt rules are the control. ([AI features and your website](https://developers.google.com/search/docs/appearance/ai-features)) Since 2026 there is also a "Search generative AI control" in Search Console: inclusion is the default, and a property inherits the choice of its parent property ([Search Console Help](https://support.google.com/webmasters/answer/16908024)). `Google-Extended` is a robots.txt token, not a crawler: it governs Gemini training and grounding outside Search, and "does not impact a site's inclusion in Google Search nor is it used as a ranking signal" ([Google's common crawlers](https://developers.google.com/search/docs/crawling-indexing/google-common-crawlers)). Google's guide lists things you can ignore: `llms.txt`, "chunking" content, rewriting for AI, seeking inauthentic mentions, and over-focusing on structured data ([AI optimization guide](https://developers.google.com/search/docs/fundamentals/ai-optimization-guide)).

**Bing and Copilot.** One set of guidelines covers Bing search, Copilot and the grounding API. For citations it asks that "facts and definitions are explicit", "important information is visible on the URL itself", each URL keeps to one topic, and key information comes early. `NOARCHIVE` keeps content out of Copilot answers; `NOCACHE` limits Copilot to the URL, title and snippet. ([Bing Webmaster Guidelines](https://www.bing.com/webmasters/help/webmaster-guidelines-30fba23a)) The page uses neither, which is right.

**OpenAI.** Four agents ([OpenAI crawlers](https://developers.openai.com/api/docs/bots)):

| robots.txt token | Purpose                                                                                                                                                                        |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |

**Anthropic.** Three agents ([Claude Help Center](https://support.claude.com/en/articles/8896518-does-anthropic-crawl-data-from-the-web-and-how-can-site-owners-block-the-crawler)): `ClaudeBot` (training), `Claude-SearchBot` (search index; blocking it "may reduce your site's visibility and accuracy in user search results") and `Claude-User` (fetches at a user's request). All honor robots.txt, and Anthropic asks that rules be set "for every subdomain". Since 2026-10-30 it also recognizes a general "no AI training" preference signal based on the IETF aipref draft.

**Perplexity.** Two agents ([Perplexity crawlers](https://docs.perplexity.ai/guides/bots)): `PerplexityBot` (search index, not used for training; "we recommend allowing PerplexityBot in your site's robots.txt") and `Perplexity-User` (user-requested fetches; "generally ignores robots.txt rules"). Perplexity adds that a firewall may need an explicit rule to let its bots through, with Cloudflare as its example.

**What these documents say about being cited.** Only this: allow the search crawler (and, for OpenAI and Perplexity, do not block its IP ranges), and for Google and Bing, be indexed with a snippet. None of the four vendors documents a way to raise the chance of a citation beyond that.

**llms.txt, honestly.**

- It is a proposal by Jeremy Howard, first published in 2024 and revised in 2026, not a standard from a standards body ([llmstxt.org](https://llmstxt.org/)).
- Google states that Search "ignores" it and that it "will neither harm nor help" ([AI optimization guide](https://developers.google.com/search/docs/fundamentals/ai-optimization-guide); clarified in the changelog on 2026-06-15).
- The crawler documentation of OpenAI, Anthropic and Perplexity, and Bing's guidelines, do not mention reading a site's `llms.txt`. OpenAI and Perplexity do publish one for their own developer docs (both pages point to it), which shows they find the format useful for documentation, not that their search crawlers consume it.
- The proposal itself says it is used "most heavily for software documentation, where coding agents follow them". nibble's site is one short HTML page that any agent can already read whole.

Conclusion: no documented search benefit. Skip it unless nibble grows documentation.

**Cloudflare's side.** Cloudflare can prepend "managed" directives to robots.txt and can block AI crawlers through AI Crawl Control ([Cloudflare](https://developers.cloudflare.com/bots/additional-configurations/managed-robots-txt/)). The site returned `200` to every AI user agent I tried, and no managed robots.txt is served, but only the dashboard shows the real setting. Worth one look.

### 9. Off-page discovery (short, and lower confidence)

These rest on each platform's own rules, but none of those rules promises visibility. Confidence that any of them moves search traffic is lower than for the on-page findings.

- **Promotion is part of Google's own advice.** "Tell people about your site. Be active in communities where you can tell like-minded people about your services." ([Search Essentials](https://developers.google.com/search/docs/essentials)) Bing counts "external links from relevant websites" as a discovery signal and forbids bought or manufactured links ([Bing Webmaster Guidelines](https://www.bing.com/webmasters/help/webmaster-guidelines-30fba23a)).
- **GitHub repository.** Topics help people "find and contribute to your project"; up to 20, lowercase with hyphens ([GitHub Docs](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/classifying-your-repository-with-topics)). The repository has none. The homepage field is already set. A custom social preview image can be uploaded (section 7).
- **Homebrew Cask.** Not available yet. A new package needs "at least 30 forks, 30 watchers or 75 stars", or 90 forks, 90 watchers or 225 stars when the repository's owner submits it, and "a code repository less than 30 days old is normally not eligible" ([Package Acceptance Policy](https://docs.brew.sh/Package-Acceptance-Policy)). Apps must pass Gatekeeper ([Acceptable Casks](https://docs.brew.sh/Acceptable-Casks)); nibble's disk image is notarized, per the recent release commits. A personal tap has no such thresholds, but I did not read Homebrew's tap documentation for this note.
- **Directories.** One checked: the `open-source-mac-os-apps` list takes a pull request that adds an entry to `applications.json` with a description, categories, repository URL, icon, screenshots and official site ([CONTRIBUTING.md](https://github.com/serhii-londar/open-source-mac-os-apps/blob/master/CONTRIBUTING.md)). I did not verify the rules of other directories.

## Open questions for the owner

1. **Which searches should find nibble?** For example "Claude Code usage tracker", "Claude Max worth it", "Claude Code cost menu bar", "is Claude Pro worth it for developers". The answer decides the title, the first paragraph and the image text. Search Console's Performance report will show real queries a few weeks after indexing.
2. **Claude Code in the title?** It is the most specific true word today, and the product plans other providers. Name it now and change it later, or keep the generic "AI subscription"?
3. **Is "menu bar" the right term for every system?** The page promises Windows and Linux too, where the term is "system tray". Today's release has a macOS file only, so "macOS menu bar app" is the truest phrase for now.
4. **AI training crawlers: allow or not?** `tonytang.dev` allows search, AI input and AI training. Should nibble's host say the same?
5. **Is there already a Search Console Domain property for `tonytang.dev`?** If so, nibble's data and its generative AI setting are already inside it.
6. **Does the Cloudflare zone block or challenge AI bots?** I could not see the dashboard.
7. **Who draws the social image?** It needs the mascot and must follow the brand rules in `design/HANDOFF.md` (yellow only for the cheese and the pupils, the teal background reserved for the paid-off moment).
8. **Is "nibble" too common a word to win as a site name?** Google may decline a name other sites share. Which `alternateName` values are acceptable: "nibble app", the host name?
9. **Is a screenshot on the page wanted**, given the hero already shows a live HTML mockup?
10. **The live download section** shows a link to GitHub Releases instead of the file list this branch builds. Is the deployed build behind?
